    NEXT 시흥 API 명세

    React 화면과 Spring Boot 서버가 주고받는 REST API를 정리한 문서입니다. 제안서의 1·2순위 기능(상태 등록, 로드맵, 정책 연결, 진행상태, 캘린더, 관리자, 맞춤 채용, 커뮤니티, 알림)을 모두 다루며, 5주차에 확정해 프론트엔드와 백엔드가 동시에 개발하는 기준으로 씁니다.

    Base URL /api/v1 인증 JWT Bearer 형식 JSON (UTF-8) 엔드포인트 0개

    기본 규칙

    모든 API는 같은 응답 껍데기와 이름 규칙을 따릅니다. 신청 자체는 서비스 안에서 처리하지 않으므로, 정책 관련 응답에는 항상 공식 신청 URL과 마지막 정보 확인일이 들어갑니다.

    항목규칙
    Base URL/api/v1, 관리자는 /api/v1/admin
    인증Authorization: Bearer {accessToken}. Access 토큰 30분, Refresh 토큰 14일. 만료 시 TOKEN_EXPIRED를 받고 재발급 API 호출
    권한 표시- 로그인 불필요 · U 로그인 사용자 · U? 선택(로그인하면 내 진행상태가 함께 옴) · A 관리자(ADMIN)
    날짜날짜 yyyy-MM-dd, 일시 yyyy-MM-dd'T'HH:mm:ss (KST). D-day는 서버가 계산해 dDay(정수, 지났으면 음수)로 내려줌
    이름URL은 kebab-case 복수형 명사, JSON 필드는 camelCase, enum 값은 UPPER_SNAKE_CASE
    ID모든 리소스 ID는 Long. 경로 변수 이름은 {policyId}처럼 리소스명 + Id
    우선순위제안서 4장 기준. 1순위 없으면 서비스가 성립하지 않는 기능, 2순위 기간 내 반드시 구현할 기능, 3순위 여유가 있으면 추가할 기능(이 명세에는 1개만 포함)

    응답·에러 형식

    성공과 실패 모두 같은 4개 필드를 씁니다. 화면은 success로 분기하고, 에러 처리는 code를 기준으로 합니다.

    성공
    {
  "success": true,
  "code": "OK",
  "message": "요청이 성공했습니다.",
  "data": { ... }
}
    실패 (입력값 오류 예시)
    {
  "success": false,
  "code": "INVALID_INPUT",
  "message": "입력값을 확인해 주세요.",
  "data": {
    "errors": [
      { "field": "email", "reason": "이메일 형식이 아닙니다." }
    ]
  }
}

    페이지네이션

    목록 API는 page(0부터), size(기본 20, 최대 50)를 받고 data를 아래 형태로 돌려줍니다.

    { "content": [ ... ], "page": 0, "size": 20, "totalElements": 135, "totalPages": 7, "hasNext": true }

    공통 enum

    화면 칩과 배지에 쓰는 값입니다. 화면 표시명은 프론트에서 매핑하고, 서버는 영문 값만 주고받습니다.

    진행상태 ProgressStatus
    TO_CHECK 확인 필요→ INTERESTED 관심→ PLANNED 신청 예정→ APPLIED 신청 완료→ IN_PROGRESS 참여 중→ COMPLETED 완료

    사용자가 직접 바꾸며 단계를 건너뛰거나 되돌리는 것도 허용합니다. COMPLETED로 바뀔 때만 응답에 suggestReview: true가 와서 1분 후기 작성을 제안합니다.

    v1.2에서 고친 것

    • 수정 온통청년 API 응답 형식: XML이 아니라 JSON(rtnType=json)으로 받음
    • 수정 채용공고 출처: '고용24 채용정보' → '사람인(승인 시) 또는 관리자 등록'. 공고 출처 enum JobSource 추가
    • 수정 GET /jobs/recommended의 dataSource: 고정 문자열 대신 공고의 source 값(JobSource)
    • 추가 POST /admin/jobs, PUT /admin/jobs/{jobId}, PATCH /admin/jobs/{jobId}/close: 사람인 승인이 안 나면 이 API로 시연 데이터 등록
    • 수정 POST /admin/sync/{source}의 source에 saramin 추가(고용24 수집이 빠져 work24는 제거)

    v1.1에서 고친 것

    • 수정 현재 상황 enum: 제안서 표기대로 '군 복무 및 전역'을 하나(MILITARY)로 합침
    • 삭제 게시글 좋아요 API 2개와 인기순 정렬: 제안서에 없는 기능이고, '후기 기반 인기 순위'는 3순위
    • 수정 DELETE /roadmap-items/{itemId}를 3순위로 표시: '로드맵 직접 편집'은 제안서 3순위
    • 수정 회원가입 birthYear를 선택값으로 바꿈: 상태 정보만 받는다는 제안서 원칙에 맞춤
    • 추가 GET /users/me/posts: 3-3 '내가 남긴 후기'
    • 추가 GET /admin/stats: 8-3 운영 지표(7일 재방문율, 관심 공고 저장 수, 후기 수), 8-2 프로그램별 관심 등록 수
    • 추가 관리자 정책 목록에 등록일(createdAt): 4-1 ⑥ 관리 항목

    제안서에 없어 명세에서 정한 값 (팀 확인 필요)

    • 인증 방식 JWT, Access 30분 · Refresh 14일
    • 수집 시각: 정책 매일 03:00, 채용공고 매일 04:00 (제안서는 '하루 1회'까지만 정함)
    • 마감 알림 시점 D-7 · D-3 · D-1, 신고 5건 자동 숨김, 마지막 확인일 30일 경과 시 '확인 필요'
    • 진행상태는 단계를 건너뛰거나 되돌리는 것을 허용
    • 관심분야에 '문화·생활'(CULTURE_LIFE) 추가: 제안서 목록은 '취업, 교육, 주거, 금융, 상담 등'
    • 로드맵 템플릿 관리 API와 외부 데이터 수동 수집 API: 제안서의 '사전에 정의·검증된 템플릿'과 시연 준비를 위해 추가
    • 관리자 공고 등록·수정·마감 API: 사람인 API 승인 전·미승인 시 시연 데이터 입력용

    스케줄러·외부 API 연동

    Spring Scheduler가 외부 데이터를 정기 수집하고 알림을 만듭니다. 인증키 승인 전에는 같은 테이블에 샘플 데이터를 넣어 두고 개발하며, 화면 쪽 API는 출처와 상관없이 그대로 동작합니다. 채용공고는 사람인 API 승인이 나지 않으면 관리자가 /admin/jobs로 직접 등록합니다.

    작업주기처리 내용결과
    청년정책 수집매일 03:00온통청년 Open API(JSON, rtnType=json)에서 전국·경기도 청년정책을 받아 policy에 저장. 같은 정책 ID는 갱신, 접수기간이 지난 정책은 CLOSEDsource=ONTONG, lastVerifiedAt 갱신
    채용공고 수집매일 04:00사람인 채용공고 API(승인 시)에서 시흥·인접 지역 신입 가능 공고 수집. 지역·학력·경력·고용형태·마감일을 정해진 칸으로 정리하고 직무명은 직무 사전으로 통일(예: 웹개발, 백엔드 → IT). 승인 전·미승인 시에는 수집하지 않고 관리자 등록 공고만 사용job_posting 저장(source=SARAMIN), 공고별 도움 되는 정책 태그 매칭
    새 맞춤 공고 알림채용 수집 직후사용자별 저장 조건과 비교해 마지막 접속 이후 새로 맞는 공고 수를 계산NEW_JOB 알림 1건 (예: "조건에 맞는 새 공고 3건")
    마감 임박 알림매일 09:00로드맵 항목·관심 공고·직접 일정 중 마감이 D-7, D-3, D-1인 것DEADLINE 알림
    새 후기 알림게시글 등록 시글에 연결된 정책·공고를 로드맵이나 관심 저장에 둔 사용자에게 발송 (작성자 본인 제외)NEW_REVIEW 알림
    오래된 정보 점검매주 월 09:00관리자 등록 정책 중 마지막 확인일이 30일을 넘은 것을 표시관리자 목록 stale=true 필터에 노출

    로드맵 생성 규칙

    AI 판단이 아니라 규칙 기반입니다. 관리자가 만든 로드맵 템플릿 중 사용자의 LifeStage와 InterestField가 가장 많이 겹치는 것을 고르고, 단계마다 연결된 정책 중 ENDED가 아닌 것을 로드맵 항목(TO_CHECK)으로 복사합니다. 상황을 바꾸면 기존 로드맵은 archived=true로 남기고 새 템플릿으로 다시 만듭니다.
